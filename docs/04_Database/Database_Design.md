# TrustLens: Database Design (v1.0)

## 1. Database Overview
TrustLens utilizes PostgreSQL as its primary relational database. The schema is designed to efficiently store user identities, digital asset metadata, complex forensic analysis results, and blockchain ledger entries. The database is optimized for integration with FastAPI, SQLAlchemy (as the ORM), and Alembic (for migration management).

## 2. Core Entities
*   **Users & Roles:** Managing access control and user profiles.
*   **Assets:** Core records representing the uploaded digital files (PDF, Image, Audio).
*   **Verifications:** The central orchestration record linking an asset to its analysis pipelines.
*   **Asset Metadata:** Extracted structural and EXIF data of the assets.
*   **AI Analysis:** Detailed deterministic metrics and AI-generated explanations.
*   **Blockchain Blocks:** Internal ledger records simulating or interfacing with a cryptographic blockchain.
*   **Reports:** The final aggregated output provided to the user.
*   **Audit Logs:** Immutable tracking of user and system actions for compliance.

## 4. Tables and 5. Table Fields with Datatypes

### `users`
*   `id` (UUID, Primary Key)
*   `email` (VARCHAR(255), Unique, Not Null)
*   `password_hash` (VARCHAR(255), Not Null)
*   `is_active` (BOOLEAN, Default True)
*   `created_at` (TIMESTAMP WITH TIME ZONE, Default NOW())
*   `updated_at` (TIMESTAMP WITH TIME ZONE)

### `roles`
*   `id` (UUID, Primary Key)
*   `name` (VARCHAR(50), Unique, Not Null) - e.g., 'admin', 'user'
*   `description` (TEXT)

### `user_roles`
*   `user_id` (UUID, Foreign Key -> users.id)
*   `role_id` (UUID, Foreign Key -> roles.id)
*   *(Composite Primary Key: user_id, role_id)*

### `assets`
*   `id` (UUID, Primary Key)
*   `user_id` (UUID, Foreign Key -> users.id, Not Null)
*   `original_filename` (VARCHAR(255), Not Null)
*   `asset_type` (VARCHAR(50), Not Null) - 'PDF', 'IMAGE', 'AUDIO'
*   `file_hash` (VARCHAR(64), Not Null) - SHA-256 hash of the file
*   `storage_path` (VARCHAR(512), Not Null)
*   `uploaded_at` (TIMESTAMP WITH TIME ZONE, Default NOW())

### `asset_metadata`
*   `id` (UUID, Primary Key)
*   `asset_id` (UUID, Foreign Key -> assets.id, Unique, Not Null)
*   `file_size_bytes` (BIGINT)
*   `mime_type` (VARCHAR(100))
*   `exif_data` (JSONB) - Raw extracted metadata
*   `structural_data` (JSONB) - E.g., PDF layers, audio channels

### `verifications`
*   `id` (UUID, Primary Key)
*   `asset_id` (UUID, Foreign Key -> assets.id, Not Null)
*   `status` (VARCHAR(50), Not Null) - 'PENDING', 'PROCESSING', 'COMPLETED', 'FAILED'
*   `trust_score` (NUMERIC(5,2)) - Calculated by deterministic engine (0.00 to 100.00)
*   `risk_level` (VARCHAR(20))
*   `started_at` (TIMESTAMP WITH TIME ZONE, Default NOW())
*   `completed_at` (TIMESTAMP WITH TIME ZONE)

### `ai_analysis`
*   `id` (UUID, Primary Key)
*   `verification_id` (UUID, Foreign Key -> verifications.id, Unique, Not Null)
*   `forensic_evidence` (JSONB) - Aggregated deterministic findings
*   `ai_explanation` (JSONB) - Human-readable explanation generated by Qwen 3 4B
*   `model_version` (VARCHAR(50))
*   `analyzed_at` (TIMESTAMP WITH TIME ZONE, Default NOW())

### `blockchain_blocks`
*   `id` (BIGSERIAL, Primary Key)
*   `verification_id` (UUID, Foreign Key -> verifications.id, Nullable)
*   `payload_hash` (VARCHAR(64), Not Null) - Hash of the asset or verification record
*   `block_hash` (VARCHAR(64), Unique, Not Null)
*   `previous_block_hash` (VARCHAR(64), Not Null)
*   `timestamp` (TIMESTAMP WITH TIME ZONE, Default NOW())

### `reports`
*   `id` (UUID, Primary Key)
*   `verification_id` (UUID, Foreign Key -> verifications.id, Unique, Not Null)
*   `report_url` (VARCHAR(512), Not Null) - Link to generated PDF/HTML report
*   `generated_at` (TIMESTAMP WITH TIME ZONE, Default NOW())

### `audit_logs`
*   `id` (UUID, Primary Key)
*   `user_id` (UUID, Foreign Key -> users.id, Nullable)
*   `action` (VARCHAR(255), Not Null)
*   `resource_type` (VARCHAR(100))
*   `resource_id` (VARCHAR(255))
*   `ip_address` (VARCHAR(45))
*   `timestamp` (TIMESTAMP WITH TIME ZONE, Default NOW())

## 6. Primary Keys
All core tables utilize `UUID` (specifically `uuid4`) as Primary Keys to ensure global uniqueness, prevent ID enumeration, and facilitate decentralized ID generation. The exception is `blockchain_blocks`, which uses an auto-incrementing `BIGSERIAL` to strictly represent chronological ledger order alongside cryptographic hashes.

## 7. Foreign Keys
*   `user_roles.user_id` -> `users.id` (ON DELETE CASCADE)
*   `user_roles.role_id` -> `roles.id` (ON DELETE CASCADE)
*   `assets.user_id` -> `users.id` (ON DELETE RESTRICT)
*   `asset_metadata.asset_id` -> `assets.id` (ON DELETE CASCADE)
*   `verifications.asset_id` -> `assets.id` (ON DELETE CASCADE)
*   `ai_analysis.verification_id` -> `verifications.id` (ON DELETE CASCADE)
*   `blockchain_blocks.verification_id` -> `verifications.id` (ON DELETE SET NULL)
*   `reports.verification_id` -> `verifications.id` (ON DELETE CASCADE)
*   `audit_logs.user_id` -> `users.id` (ON DELETE SET NULL)

## 8. Relationships
*   **One-to-Many:**
    *   User to Assets (1:N)
    *   Asset to Verifications (1:N - an asset can be re-verified over time)
*   **One-to-One:**
    *   Asset to Asset_Metadata (1:1)
    *   Verification to AI_Analysis (1:1)
    *   Verification to Report (1:1)
*   **Many-to-Many:**
    *   Users to Roles (N:M via `user_roles`)

## 9. Indexes
*   `idx_users_email` (users.email) - For rapid login lookups.
*   `idx_assets_user_id` (assets.user_id) - For fetching a user's dashboard.
*   `idx_assets_file_hash` (assets.file_hash) - To quickly check if an asset was previously uploaded.
*   `idx_verifications_status` (verifications.status) - For worker queues and dashboard filtering.
*   `idx_blockchain_blocks_prev_hash` (blockchain_blocks.previous_block_hash) - For chain validation.
*   **GIN Indexes:** Added on `asset_metadata.exif_data` and `ai_analysis.forensic_evidence` to support high-performance JSONB querying.

## 10. Constraints
*   **Unique Constraints:** `users.email`, `roles.name`, `blockchain_blocks.block_hash`.
*   **Check Constraints:**
    *   `assets.asset_type` IN ('PDF', 'IMAGE', 'AUDIO')
    *   `verifications.trust_score` BETWEEN 0.00 AND 100.00
    *   `verifications.status` IN ('PENDING', 'PROCESSING', 'COMPLETED', 'FAILED')
    *   `verifications.risk_level` IN ('LOW', 'MEDIUM', 'HIGH')
*   **Not Null Constraints:** Enforced strictly on all core data fields (e.g., hashes, filenames, statuses) to prevent data corruption.

## 11. Data Retention Strategy
*   **Assets:** Original files are temporarily stored locally during verification. Depending on user configuration, they are either purged immediately after processing or moved to scalable object storage.
*   **Database Records:** Hashes, verification metadata, and AI explanations are retained indefinitely to preserve the integrity of the audit trail and blockchain ledger.
*   **Audit Logs:** Retained indefinitely for compliance and security forensics.

## 12. Security Considerations
*   **No Sensitive PII in Verifications:** The database design strictly avoids fields for KYC, AML, or identity documents, focusing entirely on the technical parameters of the digital asset.
*   **Hash Irreversibility:** Only SHA-256 hashes of the files are stored in the core tables; the files themselves cannot be reconstructed from the database.
*   **Encryption at Rest:** PostgreSQL should be configured with disk-level encryption.
*   **SQL Injection Prevention:** Enforced inherently by SQLAlchemy ORM usage.

## 13. Future Database Extensions
*   **Version 2 (Video & Deepfake):** Expansion of `asset_type` to include 'VIDEO'. Addition of a `deepfake_analysis` table linked to `verifications`.
*   **Version 2 (Workspaces):** Introduction of `workspaces`, `workspace_users`, and `api_keys` tables to support organizational accounts.
*   **PostGIS:** Future integration of PostGIS extensions if geolocation verification of assets (via EXIF data) becomes a core trust metric.
